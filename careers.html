What we're building

We're building the transaction and ownership intelligence layer for business aviation — the system of record for what an aircraft is, who owns it, what it's worth, and what happened to it.

Currently in stealth. In closed beta with a small group of brokers and principals who use the product on live deals and tell us to our faces when it's wrong. Commercial launch 1 January 2027.

Two founders. One with 27 years in tech, media and SaaS, and multiple exits. One with 30 years in business aviation. A fractional CTO (PhD, ML) who owns infrastructure, security and the release gate. You'll work with all three.

How this codebase gets written

Almost none of it is typed by a human.

The platform — React front end, Postgres with row-level security, edge functions, a scraper fleet, LLM extraction pipelines — is built by Claude Code sessions running in parallel, each in its own git worktree, driven from Linear issues and merged through a release train that only moves via CI. Over 1,700 issues have gone through that loop since May. It ships several changes a day.

That is the job's context and the job's problem. When an agent writes the code, the quality of the product is decided by the quality of the harness around the agent: what it is told, what it is forced to check, what it cannot do, and what has to be green before a human presses merge.

Today that harness is a 700-line CLAUDE.md, sixteen skills, a couple of hooks, a Playwright suite that covers nine surfaces and no authenticated flow, and a lot of discipline held in founders' heads. It got us here. It will not get two founders, a data engineer and you safely through a launch.

Your mission

Make the harness better than the people running it — then ship through it.

Three strands, one person.

QA and release. You are the evidence behind the second gate — the human decision to promote staging to production. You build the authenticated end-to-end suite (login and MFA, deal CRUD, uploads, briefing generation, exports, Stripe in test mode) and get it running nightly on staging. You seed staging so it can be tested. You run the release smoke on staging and prod. You write defect reports that are reproductions, not impressions. You re-test fixes and say so. You think in edge cases — null input, unauthenticated, database read-only — and force the agent to test them.

Agent workflow. You own CLAUDE.md, the skills, the hooks and the sub-agents as a product. You cut the working guide to what an agent actually adheres to and move the rest into skills that load on demand. You turn every rule that must be guaranteed — verify before declaring done, no unverified success reports, cost caps on paid lanes, migrations through the right path — from prose into a hook that blocks. You build the evals that fail a merge. You teach the rest of us, by example and by review, how to run a session so it lands the first time.

Build. You are also the one engineer between the founders and the launch backlog. You run the loop — issue, plan, review, tests, QA, merge — on the Must-tier items that need a person and not a night shift: billing and access (Stripe checkout, entitlements, the free tier), tail-intelligence data fixes (provenance per field, the ownership golden set), the pre-audit security items under the CTO's review. You don't type most of it. You decide what the agent builds, you catch what it gets wrong, and you own the result.

If it works, we double down. If it doesn't, we kill it that week.

Non-negotiable: you have run this in production

Not tried it. Run it. For months, on a product with users, where a bad merge cost something.

You need all of:

  • A CLAUDE.md (or equivalent agent working guide) you wrote and maintained for a real team, and can walk us through line by line — why each rule exists, which incident put it there, what you removed and why
  • At least one hook you wrote that blocked an agent from doing something, and at least one eval or test gate you wrote that failed a merge
  • A test suite you built — Playwright, Cypress or similar — that ran in CI and caught regressions before users did
  • Production incidents you have personally caused, caught, or cleaned up. We want someone who has broken enough things to know where they break

And you need to talk about the workflow without a glossary. Context window and what actually loads into it. Why an instruction in CLAUDE.md is a suggestion and a hook is a rule. Sub-agent versus fork and when each. Worktrees. Compaction and what to preserve across it. When to stop correcting a session and restart it. Model tiering and prompt caching as cost levers, not trivia.

Haven't run Claude Code (or a comparable coding agent) on a production codebase → not a fit. Please don't apply.

"I use it every day for my own projects" is not the same thing and we will find out on the trial.

To apply

Three things. Short is fine. CVs are optional.

1. A CLAUDE.md you wrote for a real team. Paste it or link it. Then, in a few bullets: which rules earned their place through an incident, which one you'd delete tomorrow, and what you moved out of it and where.

2. The harness problem. ~400 words, bullets are fine.

You inherit an agent-written codebase. The working guide is 700 lines. It contains a 370-line section granting the agent standing authorisation to open, review and merge PRs under conditions. There is a Stop hook that runs typecheck. Every other quality rule — "verify before declaring done", "never report success unverified", "paid extraction lanes have a daily cap", "apply migrations with db push, never with the MCP tool" — is prose. Releases go out several times a day. There is no authenticated e2e suite.

a) What do you do in week one, and in what order? Be specific about what moves where.

b) Which of those prose rules become hooks, which become CI, which stay prose — and why each.

c) What's the first e2e test you write, and what has to exist before you can run it nightly?

3. Something you broke. A production incident you caused, caught or cleaned up. What happened, what you changed so it couldn't happen twice, and whether it did.
